## Cause classification

Classification: **duplicate-version**.

The workflow reached npm with valid enough Trusted Publishing/provenance state to sign and upload publish metadata, but the final registry write failed because version `0.1.2` already existed. The package's npm timestamp (`2026-07-04T11:20:33.149Z`) is inside this run and before the publish command's final `E403`, while the workflow's `npm view` guard still reported the version as publishable at `2026-07-04T11:20:37Z`. That points to a duplicate-version race/registry propagation window rather than a persistent authentication or workflow trigger failure.

## Current workflow behavior

Current `.github/workflows/publish.yml` behavior:

- Triggers on:
  - pushes to `main` that touch `package.json`, `package-lock.json`, or `.github/workflows/publish.yml`
  - tag pushes matching `v*.*.*`
  - published GitHub releases
  - manual `workflow_dispatch` with an optional `ref` input
- Checks out `${{ github.event.inputs.ref || github.ref }}`.
- Runs `npm ci` and `npm run ci` before publishing.
- Runs a one-time `npm view <name>@<version> version` guard.
- Publishes only when that guard sets `skip != true`.

The guard is useful for already-visible duplicates, but it is not atomic with `npm publish`; a version can become visible or immutable between the guard and the publish write.

## Reproducible non-publish check

Use this read-only check before any future publish/recovery attempt:

```sh
name=$(node -p "require('./package.json').name")
version=$(node -p "require('./package.json').version")
npm view "${name}@${version}" version --json
npm run ci
```

Expected result for the current source tree is that `npm view` returns `"0.1.2"`, proving the current package version is already public, and `npm run ci` validates the package without publishing.

## Smallest safe correction options

1. Documentation/process-only recovery: record this failed run as a harmless duplicate-version race because `0.1.2` is public and no release retry is needed for this version.
2. Future workflow hardening: after `npm publish`, if npm returns only `E403` with `You cannot publish over the previously published versions`, re-run a read-only `npm view "${name}@${version}" version`; if it now matches the local version, treat the job as an idempotent success and print the registry evidence. Keep other `E403` cases failing.
3. Trigger hygiene: for future release slices, prefer a single human-owned publish path for a version/tag and avoid manually dispatching the same tag while another publish path may still be in progress or propagating.

Any workflow hardening should be implemented in a separate correction issue/PR; this investigation does not change release workflow behavior.
